# Activity Diagram

An activity diagram is an extension of the UML activity diagram. It is a powerful tool for representing the sequence of actions that describe the behavior of a block or other structural element; that sequence is defined using control flow. Actions can contain input and output pins, which act as buffers for items flowing from one action to another, because the tasks that the action performs consume or produce them. An activity diagram is a kind of behavior diagram; it is a dynamic view of the system, showing the sequence of behaviors and occurrences over time. In contrast to structural diagrams (BDD, IBD, and parametric diagrams), structural diagrams are all static views that do not express any dynamic time or changes in the system and its environment.


The header of an activity diagram is named act. An activity itself is a model element and is a kind of behavior. In an activity diagram, "token flow" is the concept that runs through the whole diagram; token flow is divided into object tokens and control tokens. Note that a token is not a model element and does not need to be created in the system model. An object token represents an instance of an event, energy, or data that flows in an activity. It can represent an input or output of an activity as a whole, and it can also represent an input or output of an action in the activity. Formally, an object token represents an instance of a block, value type, or signal created somewhere in the model hierarchy (to define the type of event, energy, or data). As you might expect, multiple object tokens flow through a single execution of an activity. A control token only indicates which action of the activity is enabled at a particular moment during the execution of the activity. Multiple control tokens may flow through a single execution of an activity. That means multiple actions in the activity are enabled at the same time.

The following sections describe basic actions, object nodes, edges, redefining actions, and control nodes in detail.

## Basic Actions

An action is a node that can exist within an activity; it is the node that models the basic functional unit of an activity. An action represents some type of processing or transformation, and it occurs when the activity is executed during system operation. As shown in the following figure:

## Object Nodes

An object node is another kind of node that can exist within an activity; it models the flow of object tokens through the activity (where object tokens represent instances of events, energy, or data). Object nodes most often appear between two actions, indicating that the first action produces object tokens as output and the second action takes these object tokens as input.

1. A pin is a special object node attached to an action; it represents the inputs and outputs of the action. As shown in the following figure:

![Input Pin and Output Pin Example](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-1.png)


2. An activity parameter is another special type of object node. You attach it to the frame of the activity diagram to represent an input or output of the activity as a whole. The notation for an activity parameter is a rectangle spanning the frame of the activity diagram, as shown in the following figure:

![Activity Parameter Example](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-2.png)


3. Streaming and non-streaming behavior: Non-streaming behavior means that the next inputs and outputs can proceed only after the action completes, whereas streaming behavior allows other inputs and outputs at the same time while the action is executing.

## Edges

Object flows and control flows are the two types of edges. An object flow is used to carry object tokens and is notated as a solid line with an arrow; a control flow is an edge that carries control tokens, and a control token enables the next action, so it is notated as a dashed line with an arrow. As shown in the following figure:

![Control Flow and Object Flow Example](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-3.png)

## Redefining Actions


A redefining action is a special type of action; it includes four kinds: call behavior action, send signal action, accept event action, and wait time action.

1. A call behavior action is a specific action that invokes another behavior when it is enabled. A call behavior action can decompose a high-level behavior into a series of lower-level behaviors. As shown in the following figure:

![Call Behavior Action](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-4.png)


2. A send signal action is asynchronous; it initiates the sending without waiting for a response. As shown in the following figure:

![Send Signal Action](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-5.png)


3. An accept event action receives not only actions that send signals, but also asynchronous time events. As shown in the following figure:

![Accept Signal Action](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-6.png)

4. A wait time action can refer to an absolute time (at) or a relative time (after). As shown in the following figure:

![Wait Time Action](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-7.png)

## Control Nodes

There are 7 types of control nodes: initial node, flow final node, activity final node, decision node, merge node, fork node, and join node.

The initial node marks the starting point of an activity. Formally, it marks a position in the activity from which the flow of control tokens begins. The notation for an initial node is a small solid circle, and it usually has only one outgoing control flow. As shown in the following figure:

![Initial Node](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-8.png)


The flow final node and the activity final node are control nodes that mark the end of the flow of control tokens. However, there is a clear difference between them: when a control token reaches a flow final node, that token is destroyed, marking the end of a single control flow. When a control token reaches an activity final node, the entire activity ends, marking the end of all control flows (regardless of whether they are still executing). As shown in the following figure:

![Flow Final Node and Activity Final Node](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-9.png)

A decision node marks the start of alternative sequences in an activity. A decision node must have a single incoming edge and usually has two or more outgoing edges. Each outgoing edge is labeled with a Boolean expression called a guard, displayed as a string between square brackets. As shown in the following figure:

![Decision Node](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-10.png)

A merge node marks the end of alternative sequences in an activity. Its notation is the same as that of a decision node: a hollow diamond. They can be distinguished by the number of incoming and outgoing edges. A merge node has two or more incoming edges and only one outgoing edge. When a token - which may be an object token or a control token - reaches a merge node through any one of the incoming edges, the token is immediately offered to the outgoing edge. As shown in the following figure:

![Merge Node](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-11.png)

A fork node marks the start of concurrent sequences in an activity. The notation for a fork node is a line segment (in any orientation), and it must have one incoming edge and two or more outgoing edges. When a token - which may be an object token or a control token - reaches a fork node, it is copied to all outgoing edges. Each copy of the original token represents an independent, concurrent control flow that proceeds along its own path. As shown in the following figure:

![Fork Node](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-12.png)

A join node marks the end of concurrent sequences in an activity. The notation for a join node is the same as that of a fork node: a line. You can distinguish them by the number of incoming and outgoing edges. A join node usually has two or more incoming edges and only one outgoing edge. As shown in the following figure:

![Join Node](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-13.png)

## Activity Partitions

An activity diagram can convey not only the order of actions but also the structure that performs each action, which can be represented using activity partitions. As shown in the following figure:

![Activity Partition](../../../../zh/二次开发教程/3-MBSE接口/1-与插件相关的SysML语言要素/media/3-活动图/image-14.png)

An activity diagram is a powerful medium for communication; its advantage lies in its readability and its ability to show that a behavior has complex control logic. Choose an activity diagram when you need to show continuous behavior and need to focus on the flow of events, energy, and data between a series of actions.
